# OpenWave Studio architecture decision record

Status: accepted for implementation (initial design)
Date: 2026-11-22 (revision 1, same day: release ancestry and feed safety, updater platform keys, macOS translocation and entitlements, plugin editor windows, per-producer rings, mock audio backend; revision 2: plugin main thread per OS, portable swap procedure, microphone permission; revision 3: force-feed override scope, swap retries, launch smoke test, future items)
Implementation plan: [docs/plans/openwave-studio.md](plans/openwave-studio.md). This record owns design decisions; the plan owns ordering, acceptance checks and status. On conflict about a design choice, this record wins; on conflict about sequencing or scope of a stage, the plan wins.

## 1. Problem and requirements

OpenWave Studio is a free, open source (MIT) and portable digital audio workstation for Windows, macOS and Linux, built with Tauri v2: a Rust core and a web UI in the system webview.

Functional requirements:

- A base feature set comparable to GarageBand: multitrack audio and MIDI recording, piano roll, step sequencer and drum machine, built-in instruments and a sampler, a loop library and browser, effects, mixer, automation, tempo detection and time-stretch ("smart tempo"), templates and export.
- Processing capacity comparable to FL Studio: high track counts, a low-latency multithreaded engine, a pattern and playlist workflow, plugin hosting, advanced routing, sidechain and plugin delay compensation (PDC).
- Cross-DAW plugin compatibility in both directions: hosting third-party plugins, and shipping OpenWave's own instruments and effects as plugins other DAWs can load.
- Portable: runs from a folder without installation; with a portable marker present, settings and projects live beside the executable.
- Two update channels, `main` (stable) and `experimental`, each built from the git branch of the same name, delivered by a signed auto-updater.

Non-goals for the first major version: VST2 (hosting or export), AAX, mobile platforms, collaboration or cloud sync, video tracks, notation editing, MP3 export (see section 11), and bundling the WebView2 runtime.

Constraints: the application stays MIT-licensed, so every linked dependency in official binaries must be MIT-compatible (permissive, or file-level copyleft such as MPL-2.0). Official binaries are built by GitHub Actions on hosted runners.

crates/ow-model/           project model, edit commands, undo, serialization, migrations

crates/ow-io/              audio and MIDI device backends (cpal, WASAPI exclusive, optional ASIO)
crates/ow-media/           decoding, resampling, peak files, disk streaming, recording writer, export encoders
crates/ow-plugin-host/     CLAP, VST3, AU and LV2 hosting behind one `HostedPlugin` interface

Workspace members: `members = ["src-tauri", "crates/*"]`, with `plugins/ow-plugins` and `xtask` appended by the stages that create them (Cargo rejects members that do not exist) (`plugins/au-wrapper` is CMake, not Cargo). Each crate's `Cargo.toml` is created by the plan stage that creates the crate.

Dependency direction: `src-tauri` depends on every crate; `ow-engine` depends on `ow-dsp` directly (it wraps a `Device` in a graph node) and on `ow-plugin-host` only through traits it defines (`Node`); `ow-model` has no dependency on `ow-engine` (the compiler from model to render plan lives in `ow-engine::compile`, which depends on `ow-model`); `ow-ipc` depends only on `ow-model` types it re-exports as DTOs (`ow-model` gains an optional `ts` feature that only adds `ts-rs` derives; serialization is unchanged), and `ow-engine` depends on `ow-ipc` solely for the `TelemetryBank` the audio thread writes; `ow-media` depends on no other OpenWave crate, and `ow-engine` depends on it solely for the `AudioSource` trait its clip source node plays (the app uses `ow-media` for imports and peaks); `ow-plugins` depends on `ow-dsp`, never on the app.

`ow-dsp` (implemented in MVP slice M4) has no dependencies at all, so the built-in devices can later be exported as plugins unchanged. Its `Device` trait processes stereo audio in place with note events carrying sample offsets, and each device kind publishes fixed parameter descriptors (stable id, name, range, default, unit, linear or log scale, or a list of choices) through `DeviceInfo`; `registry::ALL` lists the built-in kinds (`builtin.synth`, then the effects `builtin.eq`, `builtin.compressor`, `builtin.reverb` and `builtin.limiter`), and the engine, the IPC layer (`ow_ipc::device_descriptors`, the `device_descriptors` command) and the UI's generic device panel all work from that list. The synth is one saw, square or sine oscillator (PolyBLEP band-limited), a trapezoidal state-variable low-pass, an ADSR envelope, 16 voices and a gain. The effects (MVP slice M5) are a three-band EQ (low shelf, peak and high shelf as RBJ-cookbook biquads with frequency, gain and Q each), a feed-forward compressor (stereo-linked peak detector, hard-knee gain computer, gain reduction smoothed in the dB domain with separate attack and release, makeup gain; no sidechain, no lookahead) and a Freeverb-style reverb (eight lowpass-feedback combs and four allpasses per channel, delay lengths scaled from the 44.1 kHz tuning to the sample rate and a fixed right-channel spread; size, damping and mix), all written in this crate with every buffer allocated in `prepare`. In the engine, `DeviceNode` runs any device as a stereo node: an instrument node has no audio inputs and plays the track's MIDI clips through a `MidiClipPlayer` held inside it (graph edges carry audio only), an effect node has stereo inputs. `compile` builds a MIDI track as such an instrument node and every enabled insert of a built-in effect kind as an effect node, in chain order, with unity pass-throughs for bypassed or unknown kinds. The player turns each clip's notes into events at timeline samples with `Timeline::beat_to_sample_index` (the rounding every timeline event uses), places them per span of the block, and releases sounding notes on stop, locate and loop wrap. Device parameters come from the model's `Device::params` at compile time, so an edit recompiles the plan (the synth's voices restart, and an effect's filter and tail memory clears). In the UI the dock under the arrangement shows the selected track's FX list (`DeviceChain`: the instrument of a MIDI track, then its inserts in order, with add, remove, bypass and select) next to the generic panel of the selected device; adding, removing and bypassing are `InsertDevice`, `RemoveDevice` and `SetDeviceEnabled` edits, each one undo step, and the view-model lives in `src/lib/devices/chain.ts`.

Mixing and mastering (editor slice M6). `compile` applies pan as a `PanNode` between a strip's inserts and its fader (`NodeKey::Pan`; absent when it would be unity). A track whose source is mono (mono audio media, or an instrument, which plays one signal on both sides) uses a constant-power law, `left = cos(t)` and `right = sin(t)` for `t = (pan + 1) * pi / 4`, so the centre is -3.01 dB on each side and the summed power is constant; a track with stereo media, a bus and the master use balance (unity at the centre, the far side attenuated by `cos(|pan| * pi / 2)`); `ow_engine::pan_gains` is the one definition. Existing projects therefore play mono tracks 3 dB quieter at the centre than before this slice. Solo follows the track rule already in `strip_audible` (bus solo is not interpreted). Sends are gain nodes tapped after the pan stage, pre- or post-fader, into the target bus; a bus or master with no source or inserts that needs a node before its pan stage or a pre-fader send gets a unity input stage (`NodeKey::Input`), and the master's and every bus's insert chain compile exactly like a track's. `Device::latency_frames` (default 0) reaches the graph through `DeviceNode::latency_samples`, so plugin delay compensation delays every parallel path to the slowest, including around a limiter on a track or on the master; the compiled plan reports the output latency, and `export::render_strip` (which `render_project` wraps) renders that many frames more and drops them, so exports and analyses are aligned to the timeline and have the requested length. `builtin.limiter` is a lookahead brickwall: the input is delayed by the lookahead (1 to 5 ms, its reported latency) while the wanted gain `ceiling / peak` (stereo-linked) is held as a sliding minimum over the lookahead, smoothed by a moving average of the same length and released with a one-pole, and the output is clamped to the ceiling, so it never exceeds it on a sample-peak basis (true peaks can still exceed it slightly). `ow-media::analysis` measures interleaved stereo offline with code written here: BS.1770-4 K-weighting (two biquads whose coefficients are derived for any sample rate), integrated loudness over 400 ms blocks with the -70 LUFS absolute and -10 LU relative gates, the short-term (3 s) and momentary (400 ms) maxima, true peak by 4x polyphase oversampling (a 192-tap Kaiser-windowed sinc, 48 taps per phase), sample peak, RMS, crest factor, stereo correlation and eight band energies from a Welch FFT, and `normalize`, a plain gain to a target loudness lowered if the true peak would pass a ceiling. The app exposes them as plain `IpcState` methods that render offline on their own plan without the control lock: `analyze(&AnalysisRequest) -> AnalysisReport` (master or one strip after its fader, whole project or a beat range) and `export_mix(&ExportOptions) -> ExportResult` (optional normalisation; `export_wav(path)` is the plain export), with the Tauri commands `analyze` and `export_mix`. The UI adds a solo button, a pan slider and an output select to every track header, bus and master strips (fader, pan, mute, output, rename and delete for a bus) below the tracks, a send list with level and pre/post for the selected track or bus, and the same FX list and panel for a bus or the master; the view-model is `src/lib/mixer/mixer.ts` and deleting a bus first reroutes what feeds it in one undo step.

Arrangement view (stage 12). The view stays DOM and Svelte (`Arrangement`, `TrackHeader`, `Lane`, `ClipView`); its logic is plain TypeScript in `src/lib/arrange/` (`view` zoom and ruler, `snap` grid, `ruler` time marks, `selection`, `markers`, `keys`, `edits`). Every change is an existing `EditCommand` sent through the command and transaction helpers, so each is one undo step and reachable from the MCP `edit` tool: recolor is `SetInfo`, reorder is `MoveTrack` or `MoveBus`, markers are `AddMarker`, `ReplaceMarker` (rename) and `RemoveMarker`, and moving or deleting several selected clips is one transaction of `ReplaceClip` or `RemoveClip`. The snap grid (off, bar, 1, 1/2, 1/4, 1/8, 1/16 beat; Alt while dragging bypasses it) and the ruler mode are view state and are not saved in the project. Shortcuts, active when focus is not in a text field: Space plays, Home and End locate to the start and end, `+` and `-` zoom, `M` adds a marker at the playhead, Ctrl or Cmd+A selects all clips, Escape clears the selection, Delete or Backspace removes the selected clips, Shift or Ctrl or Cmd-click adds clips to the selection. In development builds `window.__owPerf.scrollBenchmark()` (`src/lib/perf/`) scrolls the arrangement for 10 s and reports `{ frames, p95Ms, meanMs }`; the `100_tracks.owave` fixture (generated by `crates/ow-model/tests/fixture_100_tracks.rs`) is its workload.

## 3. Frontend

Decision: **Svelte 5 (runes) with TypeScript and Vite, managed by pnpm**. Dense views (timeline, piano roll, step grid, waveforms, meters, automation) render on `<canvas>` (2D, upgrading individual views to WebGL2 only where profiling shows a need); chrome, dialogs, browsers and inspectors are Svelte components.

| Option | Assessment |
| --- | --- |
| Svelte 5 (chosen) | Compiled, fine-grained reactivity without a virtual DOM; small runtime; Tauri's create-tauri-app has a first-class template. Many-track views update only changed nodes. |
| React | Largest ecosystem, but re-render discipline across hundreds of track rows needs constant memoization; larger runtime. |
| SolidJS | Similar performance to Svelte, smaller ecosystem and component library choice. |
| Rust-native UI (egui, iced) | Rejected: the requirement is a web UI in the system webview. |

Revisit if Svelte 5 tooling blocks a needed library, or profiling shows the canvas views cannot hold 60 fps at 200 tracks.

## 4. Engine threading and real-time safety

Threads:

- **Audio callback thread** (owned by the device backend): runs one engine cycle per buffer. It never allocates, locks a contended mutex, performs I/O or makes blocking syscalls.
- **DSP worker pool**: `N = physical cores - 1` (minimum 1, user-adjustable) threads promoted to real-time priority with `audio_thread_priority` (MPL-2.0). The callback thread participates as a worker.
- **Control thread**: owns the authoritative `Project` model, applies edit commands, maintains undo, compiles render plans and talks to the UI. Non-real-time.
- **Disk thread(s)**: prefetch streamed audio, write recordings, write peak files.
- **UI bridge thread**: reads engine telemetry at up to 60 Hz and pushes it to the webview.
- **Plugin main thread**: plugin calls the formats require on the "main thread" (CLAP main-thread calls, VST3 controller and editor calls, AU UI) go through one `MainThreadExecutor` abstraction in `ow-plugin-host`. On **Windows and macOS** it is Tauri's event-loop thread, reached with `AppHandle::run_on_main_thread` (AppKit and Win32 windows must live there). On **Linux** it is the dedicated editor/run-loop thread (section 8), because that thread owns the X11 connection and services plugin fds and timers; Tauri's GTK thread is never used for plugin calls on Linux. The host's answer to "is this the main thread?" (CLAP `thread-check`, VST3 threading assumptions) is defined by this executor and nothing else.

Model to engine: the control thread compiles the model into an immutable `RenderPlan` (node list, buffer assignments, dependency counts, latency compensation delays, clip schedules) and sends it to the audio thread over a wait-free SPSC ring (`rtrb`). The audio thread swaps plans at a cycle boundary and returns the old plan through a second ring so it is dropped on the control thread (the `basedrop` pattern). Fine-grained changes that must not rebuild the plan (parameter values, mute and solo, transport commands) travel as fixed-size messages or as atomics.

Every producer that feeds the audio thread gets **its own SPSC ring**, because `rtrb` is single-producer: control thread (plans, parameters, transport), MIDI input (one ring per `midir` callback thread), and control surfaces / MIDI-learn automation input. The audio thread drains all rings at the start of each cycle; ring capacities are fixed at stream start and overflow drops the newest message and increments a telemetry counter.

macOS: worker threads join the output device's audio workgroup (`os_workgroup_join` on the workgroup from `kAudioDevicePropertyIOThreadOSWorkgroup`) so Apple Silicon schedules them like the IO thread; through `audio_thread_priority` if it exposes this, otherwise a small FFI shim in `ow-engine`.

Parallel scheduling: the plan is a DAG. Each cycle resets per-node atomic dependency counters; workers pop ready nodes from a lock-free queue, process them and decrement successors. Track chains are coarse nodes (a track with its inserts is one node unless it feeds a sidechain), which keeps scheduling overhead small at high track counts. Buffer reuse is liveness-aware: a buffer is reused only by a node that all previous users of the buffer precede in the DAG, so reuse adds no dependencies. Nodes must not panic; a panic on any DSP thread aborts the process rather than stalling the cycle. Workers that fail real-time promotion do not join real-time cycles; the callback thread and the promoted workers carry the load.

Plugin delay compensation: every node reports latency in samples; compilation computes the longest latency path to each mixer input and inserts preallocated delay lines on shorter paths. Automation and clip schedules are offset by the compensated latency. Latency changes reported by plugins trigger a recompile on the control thread, never on the audio thread.

Real-time safety is enforced, not assumed: `assert_no_alloc` (BSD-1-Clause) wraps the engine cycle in debug and test builds; a dedicated test renders fixture projects under it.

Formats: processing in `f32`, non-interleaved buffers, maximum block 4096 frames; timeline positions as `f64` beats plus 64-bit sample counters; 960 PPQ for MIDI.

## 5. Audio and MIDI I/O

| Platform | Default backend | Additional |
| --- | --- | --- |
| Windows | WASAPI shared via `cpal` (Apache-2.0) | WASAPI exclusive/low-latency backend via the `wasapi` crate (MIT), because cpal's WASAPI host runs in shared mode; ASIO only as an opt-in build feature (below) |
| macOS | CoreAudio via `cpal` | none needed |
| Linux | ALSA via `cpal`; PipeWire and JACK via `cpal` hosts | JACK for routing with other apps |

MIDI input and output: `midir` (MIT). MIDI files: `midly` (Unlicense).

All backends sit behind an `AudioBackend` trait in `ow-io`. A **mock backend** drives the engine callback from a plain thread (or synchronously from a test) with configurable buffer size, injected input audio, timestamped MIDI events and an optional loopback (output fed back to input after a set latency). It is the "realtime path" for tests on CI runners, which have no audio hardware.

ASIO decision: the ASIO SDK is available under GPLv3 or Steinberg's proprietary license since October 2025 ([Steinberg press release, 2025-10-15](https://ocl-steinberg-live.steinberg.net/_storage/asset/808575/storage/master/Press%20Release%20-%202025-10-15%20-%20OBS%20Partnership-%20EN.pdf); [Libre Arts, 2025-11](https://librearts.org/2025/11/steinberg-relicenses-vst3-and-asio/)). Linking it would put the distributed binary under GPLv3 obligations. Official OpenWave binaries therefore ship **without ASIO**; `ow-io` exposes an `asio` Cargo feature (wrapping cpal's `asio` feature) that is off by default, so users may build an ASIO-enabled binary from source, which they then hold under GPLv3. WASAPI exclusive mode is the default low-latency path on Windows. The owner decided (2026-11-22) that ASIO stays source-build-only: no separate GPLv3 "ASIO edition" is published.

## 6. Project model and file format

Model: `ow-model` holds `Project { tempo_map, time_signature_map, tracks, buses, patterns, clips, media_pool, devices, automation, markers, settings }`. Clips on a track are either direct (audio or MIDI, GarageBand-style linear editing) or **pattern instances** that reference a shared `Pattern` (FL-style playlist). Editing a pattern updates every instance; "make unique" copies it.

Edits are `EditCommand` values applied by the control thread. Each application returns its inverse, which is pushed on the undo stack; drags and gestures coalesce into one undo step through begin/end transaction commands.

File format: a project is a **directory bundle** `Name.owave/`:

```text
Name.owave/
  project.json        model, with "format_version"
  audio/              imported and recorded media, content-hashed names
  cache/              peak files (*.owpk) and stretch caches; safe to delete
  backups/            rotating autosaves (project-YYYYMMDD-HHMMSS.json)
```

JSON via `serde_json` (diffable, easy to migrate); writes are atomic (write temp file, fsync, rename). `format_version` is an integer; `ow-model::migrate` chains `vN -> vN+1` functions and has a golden-file test per version. Any change to the serialized model, including a purely additive field, bumps `format_version` with a migration step and a golden fixture; an older build refuses a file with a higher version instead of dropping fields it does not know. Before the first save over a file of an older version, the app copies it to `backups/pre-migration-v<N>-<stamp>.json`, which autosave rotation never deletes. Versions: 1 is the original model; 2 adds the recording fields (track `input` and `monitor`, clip `take`, settings `punch_range` and `punch_enabled`). Loading is bounded: `project.json` is at most 64 MiB, ids are at most 2^53 - 1, media paths are relative under `audio/` (no Windows reserved names, no case-insensitive duplicates), and `.owz` extraction caps entries at 4 GiB each and 32 GiB in total. An archive form `Name.owz` (zip via the `zip` crate, MIT) is used for sharing and templates; opening one extracts it to a bundle.

Implemented (MVP slice M1): the app holds the project's **media root**, the folder `MediaItem.path` is relative to. It is the bundle once the project is saved or opened and a per-session temporary folder before that (created by the first import, deleted when the project is saved, replaced or the app exits). `project_new`, `project_open(path)` and `project_save(path?)` are commands wrapping plain functions on the app's `IpcState` (testable without a window); open and new send a `reset` patch that also carries the project's path (`projectPath` in `Snapshot`, a `set_project_path` operation, `null` while unsaved). Saving to a new place copies (never moves) the media into the bundle's `audio/`, writes `project.json` atomically, points the media root at the bundle, recompiles, deletes the old temporary folder and marks the project saved, so `history.dirty` clears. `media_import(path)` decodes and resamples to the project rate, stores `audio/<hash>.wav`, builds and registers the peaks and adds the `MediaItem` itself (`AddMedia`; the UI then adds clips); content already in the pool is reused. On open and save every item whose `cache/<hash>.owpk` is missing gets a background peak build and every item is registered with the peak store. `export_wav(path)` renders the mix offline (`ow_engine::export::render_project`, its own plan and offline renderer, never the realtime engine) from 0 to the end of the last clip plus one second at the project rate into a 32-bit float stereo WAV, replacing the target atomically.

Rejected: a single SQLite file (opaque diffs, awkward for large media); a single zip as the working format (rewrites on every save, fragile with multi-gigabyte recordings).

## 7. IPC between webview and engine

- **Commands** (UI to Rust): Tauri `invoke` commands carrying `ow-ipc` DTOs; types are generated to `src/lib/ipc/generated/` with `ts-rs` (MIT) so the UI and Rust cannot drift. `tauri-specta` was considered but its Tauri v2 line is still a release candidate.
- **State mirror**: on project open the UI receives a full model snapshot; afterwards the control thread emits ordered patches (`ModelPatch` with a sequence number). The UI keeps a read-only mirror in Svelte stores and never mutates it locally. A sequence gap triggers a full resync. Implemented as follows. A patch is a list of upsert, remove and order operations computed by diffing the project before and after each command, undo or redo (plus the undo and redo state), so the UI needs no copy of the edit logic; a `reset` operation replaces the whole project on open. Entity ids come from an `alloc_ids` command, because the UI cannot mint them. The control thread sends each patch on an `ipc::Channel` while holding the lock that applied it, which keeps the stream ordered; `ipc_attach` registers the channel and returns the snapshot under the same lock. After every edit that changes the sound, the app recompiles the project with `ow_engine::compile_project_metered` and swaps the plan in (`Engine::set_project`, state carried by `NodeKey`). The compiler takes a `CompileContext { media_root, sources }`: audio clips play from memory (`MemorySource`; MVP clips are never streamed), loaded and resampled to the engine rate once on the control thread and cached as `Arc` buffers keyed by (absolute path, engine rate), with source offsets scaled by `engine rate / media rate`. Media that cannot be loaded compiles to silence and is reported as `history.missingMedia` (a warning list of media ids in every patch and snapshot), never as an `engine_error`.
- **High-rate telemetry** (meters, transport position, CPU load): the audio thread writes into a preallocated `TelemetryBank` of atomics; the UI bridge thread samples it at up to 60 Hz and sends packed little-endian `f32` frames through a Tauri v2 `ipc::Channel` as raw bytes (no JSON). Only visible strips are subscribed (a lock-free bitset over 256 meter slots; the master is slot 0, then tracks in display order, then buses). The frame layout is documented in `ow-ipc::telemetry` and decoded in `src/lib/ipc/telemetry.ts`; counters that do not fit an `f32` exactly travel as integer-valued words below 2^24, and the transport position as two such words.
- **Waveforms**: peak pyramids (min/max per 64/512/4096 samples) are computed off-thread into `cache/*.owpk`; the UI requests a range through a command returning `tauri::ipc::Response` (raw bytes in the wire format `ow_ipc::peaks` fixes; the app serves them from the `.owpk` files via `ow-media`). Fallback if a payload path proves slow: a custom URI scheme (`owave://peaks/...`) fetched with `fetch()`.

- **MCP (AI agents)**: the app hosts a Model Context Protocol server so an agent can do in OpenWave what a user can, except generate music (`docs/mcp.md`). `crates/ow-mcp` (no Tauri types) holds the JSON-RPC and MCP protocol (hand-written for revision 2025-06-18: `initialize`, `ping`, `tools/list`, `tools/call`), the tool catalog with JSON Schemas generated by `schemars` from the typed argument structs and the `ow-model` edit commands (`ow-model`'s `schema` feature), and the transport. While the app runs it listens on a per-user local socket (a named pipe with a current-user-only DACL and remote clients rejected on Windows, a 0600 Unix socket in a 0700 directory elsewhere); every connection must present a random 256-bit session token from a current-user-only file (`<data dir>/mcp/mcp.json`) before it speaks MCP, and there is no network listener. `openwave-studio mcp` is a stdio relay to that socket and starts the app when none runs. `src-tauri/src/mcp.rs` implements the tools over the same plain `IpcState` and `EngineState` methods the Tauri commands use, so agent edits go through `Control` and `Session` (the UI mirror receives them as patches, undo works). Parity is enforced by tests: `COMMANDS` in `lib.rs` lists the registered commands and is checked against `generate_handler!`, every command has a tool route or a reasoned exclusion, and the `edit` schema must list every `EditCommand` variant (`strum::VariantNames`).

The audio thread never talks to IPC directly.

## 8. Plugin hosting

| Format | Platforms | Crate / approach | License | Order |
| --- | --- | --- | --- | --- |
| CLAP | all | `clack-host` ([prokopyl/clack](https://github.com/prokopyl/clack)) | MIT OR Apache-2.0 | first |
| VST3 | all | `vst3` bindings ([coupler-rs/vst3-rs](https://github.com/coupler-rs/vst3-rs), crates.io 0.3.0) plus our own host-side interfaces (`IHostApplication`, `IComponentHandler`, `IPlugFrame`, parameter changes, event lists) | MIT OR Apache-2.0; VST3 SDK itself MIT since 3.8 | second |
| AU (v2 and v3) | macOS | `objc2-audio-toolbox` / `objc2-avf-audio`: instantiate an `AUAudioUnit` and process through its render block (`renderBlock` with our own pull-input block), not through an `AVAudioEngine` graph | Zlib OR Apache-2.0 OR MIT | third |
| LV2 | Linux | `livi` (MIT) over the system `lilv` library (ISC) | MIT / ISC | third |
| VST2 | — | not supported: the VST2 SDK is discontinued and not redistributable; no clean-room path is planned | — | — |

Shared design:

- One `HostedPlugin` trait in `ow-plugin-host` adapts every format to the engine's `Device` interface (process, parameters, note and MIDI events, state save/restore, latency, editor).
- **Scanning runs out of process**: the app re-launches its own executable with `--scan-plugin <path>`, with a timeout; a crashing or hanging plugin is blacklisted, not fatal. Results are cached in `plugin-cache.json` keyed by path, size and modification time.
- Hosted plugin parameters are automatable like built-in ones (automation lanes address `(device id, parameter id)` for every format), and plugin-reported latency feeds PDC.
- **Processing runs in process** for performance. Crash isolation by out-of-process bridging is deferred; revisit if crash reports from third-party plugins become a leading cause of data loss.
- **Editor windows**: decision: **OpenWave creates plain platform windows itself** in `ow-plugin-host::editor` and passes their raw handles to plugins: Win32 (`windows` crate, `CreateWindowExW`), AppKit (`objc2-app-kit` `NSWindow`/`NSView` on the main thread) and X11 (`x11rb`, its own X connection). Rejected: Tauri's `WindowBuilder` without a webview, which requires Tauri's `unstable` feature (API may change in minor releases) and on Linux yields a GTK window whose X11 id is unavailable under native Wayland. Owning the windows also gives us the Linux run loop plugins need: one editor thread polls the X11 connection fd plus every fd and timer registered through CLAP `posix-fd-support` and `timer-support` and VST3 `IRunLoop`; that thread is the Linux plugin main thread (section 4). The Tauri webview keeps its native GTK backend; under Wayland sessions plugin editors are X11 windows through XWayland. Risk: on Wayland they cannot be parented to or stacked with the main window (kept-on-top is the mitigation); revisit when CLAP/VST3 Wayland embedding is common.
- **macOS code signing**: the app's entitlements include `com.apple.security.cs.disable-library-validation`; without it a hardened-runtime build refuses to load plugins signed by other teams or unsigned.
- **macOS microphone access**: the bundle declares `NSMicrophoneUsageDescription` (through `bundle.macOS.infoPlist`) and the `com.apple.security.device.audio-input` entitlement; without them recording captures silence or the process is terminated by TCC. Because builds are ad-hoc signed, the TCC grant is bound to the code-directory hash, so each update may prompt for microphone access again; this is documented in `docs/releasing.md`.
- Plugin state is stored in `project.json` as base64 chunks per format, plus a format-neutral parameter snapshot for recovery.

Implemented (slice M8, CLAP): `crates/ow-plugin-host` (no model or engine types; it depends on `ow-dsp` only for the note event type) and `crates/ow-plugin-fixtures` (test plugins, built by its own `build.rs`; see `docs/plugins.md`).

- **`HostedPlugin` and `PluginProcessor`** (`hosted.rs`) split an instance by thread. The control-side `HostedPlugin` answers main-thread questions through the executor (state save and load, parameter values, host requests) and queues parameter edits; its `PluginProcessor` is the audio-thread half, which the engine's `DeviceNode` runs as an `ow-dsp` `Device` (`PluginDevice`), so a hosted plugin is a node like a built-in device and its latency feeds PDC through `Device::latency_frames`. VST3 implements the same two traits.
- **`PluginCache`** keys instances by `DeviceId`, like `SourceCache` keys media, and is part of the engine's `CompileContext`. The first compile of a `clap:<id>` device instantiates the plugin (restoring `Device.state`); every later compile finds it again, so a recompile never re-instantiates. An instance is released when its device leaves the project or changes kind (the end of each compile prunes), when a project is opened or created, and when the app closes. Offline renders (export, analysis) use a `fork()` of the cache with their own instances and the live plugins' current state, so they never touch what is playing.
- **Parameter edits** on a hosted plugin do not recompile. The control layer compares each `SetDeviceParam` (and its undo and redo) with the plugin devices of the last compile; when only parameters changed it calls `HostedPlugin::set_params`, which pushes the differing values onto a lock-free `rtrb` ring owned by the instance. The audio thread drains the ring at the start of the next block into CLAP parameter events. Anything else about a plugin device (enabled, kind, state) recompiles as before.
- **Realtime.** The audio side of an instance sits behind a mutex that only the control side locks, for a few instructions, to re-activate or deactivate it; the audio thread only `try_lock`s it and, when the control side holds it, outputs the input unchanged (silence for an instrument) for that block. Events and port descriptors use preallocated buffers. The call into the plugin is wrapped in `assert_no_alloc::permit_alloc`: the guard that wraps the engine cycle in debug and test builds checks this crate's code around the call, and the plugin's own allocations (out of our hands) are allowed. `tests/rt_safety.rs` in `ow-plugin-host` plays hosted plugins through the real cycle under the guard.
- **`MainThreadExecutor`** (`executor.rs`) is the only definition of the plugin main thread. In the app (`src-tauri/src/plugins.rs`) it is `TauriExecutor` (`AppHandle::run_on_main_thread`) on Windows and macOS and a `ThreadExecutor` thread on Linux; tests use a `ThreadExecutor`. A call from another thread blocks until the main thread has run it (30 s limit), a call on the main thread runs inline. A compile (which instantiates plugins) and a save (which collects their state) wait for the main thread while they hold the control lock; that cannot deadlock because no code that takes the control lock runs on the main thread (Tauri commands run on the blocking pool, and the main thread only ever runs plugin jobs and window work).
- **Scanner.** `scan.rs` finds `*.clap` files (folders on macOS) under the OS default folders, `CLAP_PATH` and the preferences' `paths.pluginDirs`, and starts a child per file: `ow-scan <file>` (tests and tools) or `openwave-studio --scan-plugin <file>` (the app; the executable re-launches itself). The child loads the library, instantiates every plugin to read its ports, parameters (with enumeration labels), features and latency, and prints one `OW-SCAN-RESULT <json>` line. A child that dies is `crashed`, one that runs past the timeout (10 s) is `timed_out`, one that reports an error is `failed`. Records are cached in `plugin-cache.json` in the plugin cache folder, keyed by path, size and modification time (of the executable inside a macOS bundle), including the failures, so a crashing plugin is not tried again until it changes. The app scans in the background at start (cached files cost nothing), after a scan from the settings or an MCP call, and recompiles a project that uses plugins afterwards.
- **State.** A save collects every live instance's state through the executor and writes it, base64 and tagged with the format (`clap`), into the `Device.state` of a copy of the model that is serialised (or rendered); the live model is left alone, so a save adds no undo step and does not touch the dirty flag. Opening a project restores the chunk into the new instance before it is activated.
- **Requests from the plugin** (latency changed, restart, state dirty, callbacks) are noted by atomics in the host callbacks and served by `PluginCache::service()`, which the app calls every 250 ms from its plugin thread; a changed latency recompiles the project so delay compensation follows it.

Implemented (slice M9, VST3 and editors): the `vst3` crate gives bindings only, so `ow-plugin-host::vst3` supplies the host side: `IHostApplication` (with `IMessage` and `IAttributeList`), `IComponentHandler` and `IComponentHandler2`, `IPlugFrame`, `IBStream`, and preallocated `IParameterChanges` and `IEventList` objects for `process`. A VST3 instance follows the same split as CLAP (control-side object, audio side behind a `try_lock`ed mutex, edits through a lock-free ring with an overflow list so none is dropped). The component, controller and editor view are only touched on the plugin main thread, through the `MainThreadExecutor`; `set_params` converts plain values to normalised ones through the controller, which is one such call. Kinds are `vst3:<class id>`, the id being the four SDK words as 32 hex digits (the same text on every OS); state is one `OWV3` blob holding component and controller state. A plugin's reported latency is held to ten seconds of frames. Editor windows (`editor/`) are OpenWave's own Win32 and AppKit windows on the plugin main thread; they only record what the user does (close, resize) and the plugin's `service` pass, which runs on that thread every 100 ms, acts on it, so a window message never re-enters plugin code. CLAP editors embed through the `gui` extension, VST3 editors through `IPlugView`; both honour the plugin's resize requests, and removing the device, replacing the project or closing the window closes the editor and ends any gesture still open. A change made in an editor (VST3 `performEdit`, CLAP output parameter events) goes to an edit sink that the app serves from its own thread, because the main thread must not wait for the control lock: it becomes `SetDeviceParam` edits inside one transaction per gesture, and the app tells the plugin which value the model now holds (`note_applied`) so older values of a drag are never sent back. If creating an instance outlasts the caller's wait, a cleanup job queued behind the creation job releases it. Linux has no editor windows.

## 9. Plugin export (OpenWave devices in other DAWs)

Decision: **export built-in instruments and effects as CLAP and VST3 on all platforms, plus AUv2 on macOS, all under MIT.**

- Framework: **nice-plug** ([codeberg.org/RustAudio/nice-plug](https://codeberg.org/RustAudio/nice-plug), ISC, crates.io 0.4.x), the community-maintained successor to nih-plug, which its author has put in maintenance mode ([nih-plug README](https://github.com/robbert-vdh/nih-plug)). Upstream nih-plug's VST3 export uses `vst3-sys`, which is GPLv3, so its VST3 binaries must comply with GPLv3. nice-plug's `vst3` feature instead depends on `vst3 = "0.3.0"` (verified in `crates/nice-plug/Cargo.toml` on 2026-11-22), the MIT/Apache-2.0 coupler-rs bindings.
- Steinberg moved the VST 3 SDK to the MIT license with version 3.8 (October 2025) and no longer offers the GPLv3/proprietary options ([VST 3 license page](https://steinbergmedia.github.io/vst3_dev_portal/pages/VST+3+Licensing/VST3+License); [3.8.0 change log](https://steinbergmedia.github.io/vst3_dev_portal/pages/Versions/Version+3.8.0.html); [Sound On Sound](https://www.soundonsound.com/news/steinberg-adopt-mit-license-vst3)). The "VST" name and logo remain Steinberg trademarks: OpenWave uses "VST3" only as a descriptive format name, does not use the logo, and checks Steinberg's usage guidelines before the first plugin release.
- AU: [clap-wrapper](https://github.com/free-audio/clap-wrapper) (MIT; AudioUnitSDK Apache-2.0) builds an AUv2 that dynamically loads the Rust-built `.clap`. It is a CMake/C++ step on the macOS runner only. If it proves unworkable, macOS users keep CLAP and VST3 (revisit condition).
- DSP is shared: each device lives in `ow-dsp` behind the `Device` trait; `ow-plugins` adapts it to nice-plug's `Plugin` trait, so the in-app device and the exported plugin produce identical output (tested).
- GUI: in the app, devices use Svelte panels; exported plugins use `nice-plug-egui` editors generated from the same parameter descriptors.
- Distribution: a separate release asset `OpenWave-Plugins-<version>-<platform>.zip` with `.clap`, `.vst3` and (macOS) `.component` bundles, built and attached on **both** stable and experimental releases (owner decision 2026-11-22). On macOS the bundles are ad-hoc signed and not notarized (section 10), so users may need `xattr -dr com.apple.quarantine <bundle>` before a DAW will load them; `docs/plugins.md` says so.
- Licence guard: CI runs `cargo deny check licenses` with an allowlist (MIT, Apache-2.0, BSD-*, ISC, Zlib, Unicode, MPL-2.0, Unlicense, CC0) and denies GPL/LGPL/AGPL, so a GPL dependency cannot slip back in. Fallback if a GPL dependency becomes unavoidable for VST3: ship CLAP-only plugins (CLAP is MIT) rather than relicensing.

## 10. Release CI, update channels and portable builds

Modelled on the Imperium-AI workflows (`ci.yml`, `build.yml`, `release.yml`, `experimental.yml` and `scripts/ci/*`):

| Workflow | Trigger | Behaviour |
| --- | --- | --- |
| `ci.yml` | pull requests, pushes to `main` and `experimental`, merge queue | docs lint, actionlint, Rust (fmt, clippy, test, cargo-deny) on Windows/macOS/Linux, web checks, plugin validators; a `source branch` job rejects PRs into `main` whose head is not `experimental`; a final `CI gate` job aggregates results |
| `build.yml` | `workflow_call` with `channel` and `version` | matrix: `linux-x64` (ubuntu-22.04: appimage, deb, rpm), `linux-arm64` (ubuntu-22.04-arm: appimage, deb, rpm), `windows-x64` (nsis), `windows-arm64` (nsis), `macos-universal` (app, dmg); builds with `tauri-apps/tauri-action` (v1 line; its release tags are named `action-vX.Y.Z`, so the commit SHA of the chosen `action-v1.x` tag is resolved and pinned in stage 2) in build-only mode (no `tagName`/`releaseId`), passing `--target`, `--bundles` and `--config` with the version and `createUpdaterArtifacts`; collects `artifactPaths`, portable packages and plugin bundles into `dist/`, signs portable zips with `tauri signer sign` and fails if any updater artifact lacks a `.sig`; uploads `openwave-<channel>-<id>` workflow artifacts |
| `release.yml` | tags `v*` excluding `v*-experimental*` | `prepare` (checkout with `fetch-depth: 0`) derives version and pre-release flag (hyphen means pre-release) and fails unless `git merge-base --is-ancestor "$GITHUB_SHA" origin/main`, so the main channel only ships commits on `main`; `build` calls `build.yml`; `publish` creates the GitHub Release (`--latest` for stable), writes `SHA256SUMS`, then updates the `main` feed (non-pre-releases only), then prunes older main releases |
| `experimental.yml` | push to `experimental`, manual dispatch | `prepare` fails unless the ref is `experimental` and `git merge-base --is-ancestor "$GITHUB_SHA" origin/experimental`; version `X.Y.<run_number>-experimental` from the app version; pre-release with `--latest=false` at the built SHA; then the `experimental` feed is updated; then older experimental releases are pruned |

Publication order and feed safety: (1) the versioned release with all assets is created, (2) the feed's `latest.json` is uploaded, (3) older releases are pruned, so the feed never points at a missing asset. Feed-updating jobs share `concurrency: { group: updater-feed-<channel>, cancel-in-progress: false }`. Before uploading, the publish script downloads the current feed and skips the upload if the feed's version is greater than the one being published (a late-finishing older run cannot roll the channel back). After upload it requests every URL in the new `latest.json` and fails unless each returns HTTP 200. An intentional version reset (for example after a mistakenly high version) uses a manual `workflow_dispatch` input `force_feed: true` (on `experimental.yml`, and on `release.yml` only when dispatched on a tag ref), which skips the "newer feed wins" check for that run only and never the branch-ancestry check; the procedure is documented in `docs/releasing.md`.

Differences from Imperium, with reasons:

- Builds use `tauri-action` in build-only mode instead of a hand-written `tauri build` script, as requested; the publish step stays a script because tauri-action's own `latest.json` upload assumes one release per feed.
- **Feed hosting**: each channel has a fixed-tag GitHub Release that holds only the feed: `updater-main` and `updater-experimental`, each with an asset `latest.json` replaced by `gh release upload --clobber`. Endpoint: `https://github.com/Densetsu152637/OpenWave-Studio/releases/download/updater-<channel>/latest.json`. Imperium instead lists releases through the GitHub REST API at runtime, which is limited to 60 unauthenticated requests per hour per IP; a static asset URL has no such limit and needs no client logic. A gh-pages endpoint was rejected because it adds a branch and Pages deploy latency for no gain. Feed tags start with `updater-`, so they never match the `v*` release trigger.
- Windows ships NSIS only (no MSI), which removes MSI's pre-release version problem and gives one updater artifact per Windows target. RPM is skipped for pre-release versions (it rejects the hyphen), as in Imperium. Empty signing secrets are unset before building.

Updater (`tauri-plugin-updater` 2.x): `pubkey` in `tauri.conf.json`; `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` are repository secrets; updater artifacts are the signed NSIS `-setup.exe` on Windows, `.app.tar.gz` on macOS and the AppImage on Linux ([Tauri updater docs](https://v2.tauri.app/plugin/updater/)). Feed platform keys, one per matrix target, with installer-specific keys so a future second installer type cannot be confused:

| Key | Artifact |
| --- | --- |
| `windows-x86_64`, `windows-x86_64-nsis` | `_x64-setup.exe` |
| `windows-aarch64`, `windows-aarch64-nsis` | `_arm64-setup.exe` |
| `windows-x86_64-portable`, `windows-aarch64-portable` | signed portable zips |
| `darwin-x86_64`, `darwin-aarch64` (and `-app` variants) | `_universal.app.tar.gz` |
| `linux-x86_64`, `linux-x86_64-appimage` | `_amd64.AppImage` |
| `linux-aarch64`, `linux-aarch64-appimage` | `_aarch64.AppImage` |

deb and rpm installs do not self-update (the Tauri updater replaces only AppImages on Linux). On Linux the app treats itself as package-managed when `$APPIMAGE` is unset: automatic checks are off and the update panel says "Update OpenWave Studio through your package manager".

The app builds its updater at runtime with `updater_builder().endpoints([feed_url(channel)])`. The channel defaults to the one the running version was released on (version contains `-experimental` or not) and can be switched in settings. Directly after a switch, one check runs with a version comparator that accepts any different version, so moving from experimental back to main can "downgrade"; the relaxed comparator is not persisted, and every later check uses the normal "newer only" rule. Checks run 20 s after start and every 6 h; updates download in the background and install on quit, on "Restart to update", or through `update_install_now` ("Check and install updates", which checks, downloads, installs and restarts in one step) (Windows `installMode: passive`).

Portable builds and self-update:

| Platform | Portable artifact | How it updates |
| --- | --- | --- |
| Windows | `OpenWave-Studio_<v>_<arch>_portable.zip` (plain exe built with `--no-bundle`, `portable` marker file, licenses) | custom path: the feed also carries `windows-<arch>-portable` entries; the app calls `check()` with that custom target, `download()` (which verifies the minisign signature), extracts to `<dir>/.update-staging/`, then relaunches a copy of itself from the temp directory with `--apply-update`. The helper handles that flag in `main()` before any Tauri initialization, waits for the main process to exit, and swaps files: every top-level entry of the install folder except `OpenWave Studio Data/`, the `portable` marker and `.update-staging/` is renamed to `<name>.ow-old`, the new entries are moved in, and on any error every moved-in entry is removed and every `.ow-old` renamed back, leaving the old version intact. Each rename is retried with backoff within a 30 s total budget (antivirus and indexer locks), and staged entries named `portable` or `OpenWave Studio Data` are never moved in. The program file is backed up last and its replacement moved in immediately after. On success the new exe is relaunched at once with `std::process::Command`, then the `.ow-old` entries are deleted; a failed update is reported at the next start via `OpenWave Studio Data/logs/update-failed.txt` |
| Linux | the AppImage itself (place a `portable` marker beside it) | the standard updater replaces the AppImage file in place |
| macOS | `OpenWave-Studio_<v>_universal_portable.zip` containing the `.app` and a `portable` marker beside it | the standard updater replaces the `.app` bundle in place |

Portable mode: at startup the app looks for a file named `portable` beside the executable (Windows), beside the AppImage (`$APPIMAGE`, Linux) or beside the `.app` bundle (macOS; not inside it, which would break code signing). If present, all settings, caches, plugin cache, logs, the WebView2 user-data folder and the default projects directory live under `<that folder>/OpenWave Studio Data/`; otherwise platform directories from Tauri's path resolver are used. Tauri has no official portable mode ([tauri-action README](https://github.com/tauri-apps/tauri-action)), so this is our own `paths` module. On Windows the WebView2 runtime must already be present (it ships with Windows 10 and 11).

macOS signing (owner decision 2026-11-22: no Apple Developer ID for now): macOS builds are **ad-hoc signed** (`bundle.macOS.signingIdentity: "-"`, which Apple Silicon requires at minimum and which still embeds the entitlements from section 8) and **not notarized**. Gatekeeper therefore blocks the first launch of a downloaded copy; the documented workaround (README, `docs/portable.md`) is right-click › Open (or System Settings › Privacy & Security › Open Anyway on newer macOS), or `xattr -dr com.apple.quarantine "/path/OpenWave Studio.app"`. Updates installed by the updater are not quarantined, so the workaround is needed only once per manual download. Developer ID signing and notarization remain a future optional step: `build.yml` uses them only when the `APPLE_*` secrets are present (as Imperium does), with no other change.

macOS App Translocation (more important without notarization, since every browser-downloaded copy is quarantined): a quarantined `.app` launched from where it was unzipped runs from a randomized read-only path (`/private/var/folders/.../AppTranslocation/...`), so the marker beside it is invisible and the updater cannot replace the bundle. The app detects a path containing `/AppTranslocation/` (or `SecTranslocateIsTranslocatedURL`) and shows a blocking prompt explaining how to move the app (with its `portable` marker) to another folder, or how to clear quarantine with `xattr -dr com.apple.quarantine`, before portable mode and updates are enabled. This is documented in `docs/portable.md`.

## 11. Media, time-stretch and export

- Decoding: `symphonia` (MPL-2.0, file-level copyleft, compatible with MIT distribution): WAV, AIFF, FLAC, MP3, Ogg Vorbis, AAC/ALAC where supported.
- Sample-rate conversion: `rubato` (MIT OR Apache-2.0).
- Implemented (stage 11): `symphonia` 0.6 with only the wav, aiff, flac, mp3, ogg, vorbis, pcm and id3 features (no AAC/ALAC yet). Import resamples to the project rate and stores `audio/<hash>.wav` as 32-bit float WAV, where the hash covers the source bytes and the project rate (so re-importing the same file at the same rate deduplicates); the whole decoded file is held in memory during import, bounded by `ImportLimits` (default 2^27 samples, 2 GiB file, 8 channels). Peak files `cache/<hash>.owpk` carry a versioned header and three min/max levels (64, 512, 4096 frames per entry, min/max over all channels). Clips up to 30 s (configurable) play from memory; longer ones stream through a prefetch thread and two `rtrb` block rings, the stream has two lanes (each its own pair of rings and read position); `seek_hint(frame)` aims the spare lane while playback continues undisturbed, and a read at exactly that frame switches lanes with no underrun (a gapless loop wrap), while any other discontinuity re-aims the active lane and is silent until the disk thread catches up. Resampling aligns the output to the input time grid (checked against an analytic sine), refuses results over the sample limit before allocating, and bundle WAV headers are clamped to the file; writes into the bundle use unique temp files, sync and rename.
- Time-stretch and pitch-shift: `signalsmith-stretch` (MIT) for warp, smart tempo and real-time key changes; rendered stretch results are cached under `cache/`. Rubber Band was rejected (GPL).
- Tempo and beat detection: onset detection plus a Fourier tempogram implemented in `ow-dsp` (no suitable permissive crate verified).
- Implemented (stage 22a, DSP and library; clips, engine playback and UI are stage 22b): `ow-dsp::stretch` wraps Signalsmith Stretch (MIT, header-only C++), vendored unmodified in `crates/ow-dsp/vendor/signalsmith-stretch/` (with the `signalsmith-linear` FFT headers it includes; both MIT, licence files kept, provenance in its README) behind a small C ABI in `crates/ow-dsp/native/` (every call catches C++ exceptions and reports failure; `Stretcher::new` returns an error, `stretch_to_length` falls back to silence of the exact length, and non-finite samples count as silence in stretch and analysis) that `crates/ow-dsp/build.rs` compiles with `cc` and Rust declares by hand, so a build needs a C++ compiler but no libclang or bindgen. The vendored code is not a crate, so `cargo deny` does not see it and this paragraph is its third-party notice (no `THIRD_PARTY` or `NOTICE` file exists yet). `stretch_to_length(input, channels, rate, target_frames, pitch_semitones)` renders offline with the library's `exact` mode, which compensates the algorithm latency so output frame 0 lines up with input frame 0, and returns exactly `target_frames` frames per channel; a target shorter than twice the output latency is rendered with proportional zero padding and cut back, so the length is exact for every target (checked 0.5x to 2x). The pitch shift is independent of the tempo change (+-24 semitones). `Stretcher` is the streaming form: `Stretcher::new(channels, rate, max_block)` allocates and warms up the library's scratch buffers at both ratio extremes, `process(input, output, ratio)` (ratio = output over input duration, 0.25 to 4) consumes `output_len / ratio` input frames with the fraction carried between blocks and returns how many it consumed, `seek` primes the algorithm with the audio before a start position, `latency_frames` reports the output latency. The Rust side of `process` is allocation-free (checked under `assert_no_alloc` over a ratio sweep); allocations inside the C++ library go through `malloc` and are invisible to that guard, which is why the warm-up exists.
- Implemented (stage 22a, analysis): `ow-dsp::analysis::detect_tempo` (pure Rust, own radix-2 FFT) builds an onset curve from the log spectral flux of eight octave-wide bands (so a kick, snare and hat weigh alike), subtracts a moving average and squares it, then scores candidate tempi from 60 to 200 BPM by the Hann-windowed Fourier magnitude of the curve at the first four harmonics times a log-Gaussian prior (110 BPM, 1.5 octaves wide); a period-doubling check moves to half the tempo while its fundamental is at least half as strong, and the result is refined to 0.05 BPM. The first beat is the best phase of a comb of that period over the curve, and the first downbeat (4/4 assumed) the beat out of four with the most low-band onset energy, so it needs a few bars and an accent on count one to be right. Only the first 90 s are analysed; shorter than 2 s gives no tempo. The generated fixtures (drum loops at 70, 90, 100, 120, 128, 140 and 174 BPM, two with a triplet swing, one sparse kick-only pattern at 100) are all within 0.01 BPM; octave choice remains a judgement for loops whose accents do not show the beat level. `detect_key` computes a chromagram (8192-point frames at 44.1 kHz, spectral peaks from 80 Hz to 2 kHz refined by parabolic interpolation, each peak also credited to the classes of its sub-harmonics f/2 to f/6 with weight 0.6 per step, so overtones support the chord tone) and correlates it with the 24 Krumhansl-Kessler key profiles; the result carries the Pearson correlation and a confidence from the margin over the runner-up. No tuning offset is estimated.
- Implemented (stage 22a, library): `ow-media::library::scan(roots, options)` walks folders recursively (no symbolic links to folders, depth 32), decodes WAV, AIFF, FLAC, Ogg Vorbis and MP3 with the import decoder, and records duration, rate, channels, the detected tempo (dropped below confidence 0.3, so pads have none) and key from a mono mixdown, a tempo and key from the file name (`120bpm`, `bpm 128`, `Am`, `C#min`, `A minor`; a bare note letter is never a key), and tags from folder names (including the root's) and file-name words. Analysis runs on at most 4 worker threads, each decoding one file of at most 2^26 samples (256 MiB), so a scan peaks near 1.3 GiB; files over 128 MiB (configurable) are listed with an error instead of analysed, as are files whose metadata cannot be read; symbolic links found inside a root, to files or folders, are skipped. The index is a versioned JSON cache (`INDEX_VERSION` 1) keyed by path, size and modification time plus the analysis version and the size limit in force (so raising the limit re-analyses skipped files), written through a temporary file and a rename; files unchanged since the last scan are not decoded again (undecodable ones are cached with their error), tags are recomputed on every scan, and a cache with another version or damaged JSON is ignored. `LibraryIndex::search` filters by text (all words in the path or tags), tags, tempo range (optionally also half and double time) and key. `preview_in_tempo(pcm, source_bpm, target_bpm, semitones)` and `preview_entry(entry, target_bpm, semitones)` return the loop stretched to `round(frames * source / target)` frames with `stretch_to_length` (limit: a tempo change of 4x either way); `warp_target_frames` is the shared length formula. Not yet: warp markers in `Clip` (they need a model format version 3), follow-project-tempo playback, the browser UI and content-pack download (the content source is open question 3).
- Implemented (stage 22b, integration): project format version 3 adds `MediaItem.tempo` and `key` (detected on import; `media_import` analyses files up to ten minutes with `ow_media::library::analyse_pcm`, after the control lock is released) and `ClipContent::Audio.warp` (`mode` off or follow_tempo, `source_bpm`, `markers` of source frame and clip-local beat, `transpose_semitones`); all are serde defaults that are left out when unset, so the v2 to v3 migration rewrites nothing and a v2 file still loads (and is copied to `pre-migration-v2-*.json` before the first save). A warped clip plays from memory like any other: `ow-engine::clips::warp::plan` cuts the clip into segments at its markers and the tempo map's changes (and at every beat under a tempo ramp), `render` stretches each to the exact number of timeline frames with `stretch_to_length` (a segment needing more than 4x either way is silent, one that needs no change and no pitch shift is copied), and `SourceCache::warped` keeps the buffer in memory and in `cache/warp-<key>.wav`, keyed by the media hash, the engine rate, the pitch shift and the segment table (so it survives restarts, ignores unrelated tempo edits and is safe to delete; at most 96 files and 48 buffers are kept). Rendering happens in `compile_project`, on the control thread: a tempo change is a recompile, the audio thread keeps playing the previous plan until the plan with the finished render is swapped in, and offline exports render the same buffers, so the realtime path and the export agree and nothing stretches on the audio thread. A clip over 2^27 frames, or one that fails to render, plays unstretched. The loop browser (`src/lib/browser/`) lists the scan of the folders in `paths.libraryDirs`: `library_scan` (cache, progress counters and cancellation through `ScanControl`), `library_scan_status`, `library_scan_cancel`, `library_search`, `library_preview` and `library_preview_stop` (MCP tools `library_scan`, `library_search`, `library_preview`). The audition decodes and stretches the file with `preview_in_tempo` to the project tempo at beat 0 on the blocking pool and hands the finished buffer to `Engine::start_preview`: a `Preview` travels through a dedicated ring of the control link, the audio thread adds it to the output after the plan has rendered (a 64-frame fade in, a 480-frame fade out when stopped or replaced) and returns it through a retire ring, so the audio thread never frees it and `rt_safety` covers it; only files in the scanned index can be previewed. A loop added from the browser (double-click or Add) is one transaction (import, track when needed, clip) and gets `warp` follow_tempo at its own tempo, preferring the tempo in the file name over the detected one, when its tempo is known and it has at most 32 bars; its length is the whole number of beats it is within 0.1 beat of. Not done: content-pack download, warp marker editing in the UI, real-time stretching, automatic warp of recorded takes.
- Recording and WAV export: `hound` (Apache-2.0). FLAC export: a permissive FLAC encoder crate chosen in the export stage after license verification. MP3 export is a non-goal until a non-LGPL encoder path is settled.
- Implemented (MVP slice M3, audio recording): arming is session state, a set of audio track ids in the app's control layer shown through the mirror as `history.armedTracks` (never saved, no undo step, no dirty flag, cleared when another project is loaded or the track is deleted). `record_start` creates one `ow-media` `RecordWriter` per armed track (32-bit float WAV in a private temporary folder, mono for a one-channel input, otherwise channels 0 and 1) and hands the producers to the audio thread as one `RecordSet` through a dedicated ring of the engine's control link; the retire ring brings the set back, so the audio thread never frees a ring. While the transport is recording, `AudioCore::process` pushes the device input into every producer with no allocation, lock or I/O (covered by the `rt_safety` guard). Placement: a sound the engine plays is heard back on the input one round trip later (`StreamInfo::latency_frames`, input plus output: the mock backend reports its loopback latency, cpal an estimate of two callback buffers), so a take starts at the record start position minus that latency, clamped at 0 with the take's leading frames that belong before 0 dropped. Stopping (`transport_stop`) ends the recording on the audio thread first and only then finishes the writers, so a take holds every frame that was pushed; the app then imports each take like `media_import` (content hash into `audio/`, peaks built and registered, resampled when the project rate differs) and adds `AddMedia` and `AddClip` for every take in one "Record" transaction, converting the sample start to beats with the project's tempo map. A project replaced while recording discards the takes. Stage 14 (below) adds input routing, monitoring, punch, loop takes, comping and count-in. macOS needs `NSMicrophoneUsageDescription` (`src-tauri/Info.plist`) and the `audio-input` entitlement (`src-tauri/entitlements.plist`), both present.
- Implemented (stage 14, model, engine, control and MCP): recording follows the project. `Track.input` (`mono(c)` or `stereo(c)`, `None` = channel 0 / the pair 0 and 1) and `Track.monitor` (`off`, `auto`, `on`) are serde-default model fields set by `SetTrackInput` and `SetTrackMonitor`; `ProjectSettings.punch_range` and `punch_enabled` are set with `SetSettings`; `Clip.take` (`group`, `index`, `active`) marks a take and `SetActiveTake` makes one take of a group the active one in a single undo step (the model refuses a second active take in a group, and an inactive take compiles to nothing, so it is silent). The tap no longer works per device buffer: `AudioCore::cycle` hands every plan chunk's `BlockTiming` to `RecordSet::tap`, which records exactly the frames `Span::record_frames` names (never the count-in, only the punch range when set) and, when the transport loops, moves to the next pass's producer at the wrap frame (a position that does not continue the previous span while a loop is set). A pass is a take: the control layer prepares `MAX_LOOP_TAKES` (16) writers per armed track when a loop range is set, passes beyond them are dropped and counted (`RecordShared::dropped_passes`), and each pass is placed at its first recorded position minus the round-trip latency. `Engine::start_recording_plan` also sets the transport's loop, punch and count-in (cleared at stop). Monitoring is a graph node, not part of the tap: the compiler adds an `InputMonitorNode` to a monitoring audio track's clip sum (pre-inserts) and an `InputBus` to the plan; the audio thread de-interleaves each chunk's input into the bus between cycles, and automatic monitors read the track's arm flag (`ArmedTracks` in `CompileContext`, set by the control layer when arming) with a 2 ms fade. Monitoring has no feedback protection: an input that hears the output (speakers, digital loopback) feeds back when monitoring is `auto` or `on`, which is the user's choice. A loop recording prepares at most 64 take writers in all (16 passes per track for up to four armed tracks, never fewer than 2). The live engine's plan also carries the `MetronomeNode`, so the count-in clicks are audible (offline renders have none). `record_loopback` drives the mock device by hand with injected ramps to check punch, loop boundaries, count-in and routing to the sample, and a `--release` test records 16 tracks for ten simulated minutes with every writer thread running and asserts no ring overran.
- Implemented (stage 14, UI): `src/lib/record/` holds the view-model logic (input choices from the input device's channel count, monitor cycling, loop and punch range drags on the snap grid, take grouping and the take badge, deleting an active take) and the components only draw it. The track header of an audio track has an input selector and a monitor button (off, auto, on). The transport has Loop, Punch and count-in controls and shows "Count-in" while counting in. The loop range is a bar in the lower strip of the ruler (Shift+drag the ruler to create it; drag its ends or body to edit; double-click to clear); the punch range is dragged out in its own thin strip under the markers (Alt skips the snap grid in both). Each gesture is one `set_settings` transaction. Takes of one group show only the active take on the lane, with a "Take n/N" menu that sets the active take; deleting the active take first activates the nearest earlier remaining take in the same undo step. A group left without an active take (an agent deleted it) shows its first take dimmed with a "No active take" menu that repairs it. Mute and clip gain apply to the take they are set on, so switching takes can change what is muted or how loud; a move carries the whole group, and split, duplicate and trim-left/right are refused while the group has two or more takes (fades stay usable). Problems from stopping a recording (dropped loop passes, failed takes) arrive as the rejection of `transport_stop` and show as a notice.
- Loops and instrument samples ship as separate downloadable content packs (CC0 or similarly licensed content), not inside the application binary.

## 12. Testing strategy

- **Unit and property tests** (`cargo test`, `proptest`): model commands and undo/redo invariants (apply then inverse restores state), tempo-map conversions, serialization round trips, migrations against golden files.
- **Realtime-path tests**: the mock `AudioBackend` (section 5) runs the engine through its callback with fixed buffer sizes, timestamped synthetic MIDI and loopback input, so recording, MIDI timing and "realtime equals export" checks run on CI without audio hardware.
- **Manual checks** are kept to what needs real hardware or third-party software; each has a written procedure, a numeric threshold and is recorded in the plan stage's Outcome (OS, build version, hardware, result).
- **Offline render tests**: fixture projects in `crates/ow-engine/tests/fixtures/` rendered offline; output compared to reference renders within a tolerance (`-90 dBFS` difference) and deterministic across thread counts.
- **Real-time safety tests**: engine cycles under `assert_no_alloc`; plan swaps under load.
- **Performance benchmarks** (`criterion`): DSP kernels and a track-count benchmark (target, an estimate until measured: 200 tracks with a synth and three effects each at 128-frame buffers, 48 kHz, under 70% of the callback budget on an 8-core desktop). Benchmarks run in CI for trend tracking, not as a gate.
- **Plugin tests**: the host is tested against OpenWave's own exported CLAP and VST3 plugins (dogfooding); exported plugins are checked with `clap-validator` and Steinberg's VST3 `validator` in CI.
- **UI**: `vitest` for stores and IPC adapters against a mocked `invoke`; `svelte-check`; end-to-end smoke tests via `tauri-driver` (WebDriver) on Linux and Windows runners (macOS has no WebDriver support for WKWebView).
- **CI-first**: these suites run in GitHub Actions; local runs are for focused debugging.

## 13. Risks, revisit conditions and open questions

Risks:

- nice-plug is young and describes itself as experimental; pin versions and keep the `Device` to nice-plug adapter thin so another framework (or direct `clack-plugin` plus `vst3`) can replace it.
- `clack` and `vst3` are pre-1.0 with breaking changes possible; pin and wrap behind `HostedPlugin`.
- Webview rendering performance on Linux (WebKitGTK) is the weakest target; canvas views must be profiled there first.
- Plugin GUIs under Wayland rely on XWayland and cannot be parented to the main window.
- Third-party license notices: clap-wrapper (MIT) and AudioUnitSDK (Apache-2.0) in AU plugin bundles, and lilv/serd/sord/sratom (ISC) bundled in the AppImage for LV2 hosting, need their notices shipped; this is a manual check recorded in `docs/plugins.md` and `docs/audio-devices.md` by the owning stages.

Future items (not scheduled; each needs an owner decision or resources):

- Windows Authenticode code signing of the installer, exe and portable zip contents, to reduce SmartScreen warnings (needs a certificate; Azure Trusted Signing or an OV/EV certificate).
- Apple Developer ID signing and notarization (needs an Apple Developer account; `build.yml` already uses them when `APPLE_*` secrets exist), which would remove the Gatekeeper workaround and translocation prompt.
- Native Wayland embedding of plugin editors, once CLAP and VST3 Wayland GUI support is common.
- Out-of-process plugin bridge (sandboxed plugin processes with shared-memory audio) for crash isolation.

Revisit when: plugin crashes become frequent (add out-of-process bridging); WASAPI exclusive proves insufficient for users with ASIO-only hardware (reconsider an ASIO edition); clap-wrapper AU builds fail on CI (drop AU export); a permissive MP3 encoder path appears (add MP3 export).

Open questions for the project owner:

1. Source of loop and instrument content (commission, CC0 collections, community) and whether content packs are in scope for 1.0.

Resolved by the owner on 2026-11-22: ASIO stays source-build-only (no GPLv3 edition); plugin bundles ship on experimental releases too; no Apple Developer ID for now (ad-hoc signing, no notarization, section 10).
